# 桌面更新发布操作手册

把 GitHub Release 上的 `desktop-release-manifest.json` 导入 EdgeKV，让客户端能查到新版本。协议与字段定义见 [`15-桌面更新服务协议.md`](15-桌面更新服务协议.md)；本文讲操作流程、产物命名与体积口径。

## 工作流概览

`.github/workflows/build-desktop.yml` 目前只构建**两个平台**——Windows x64 与 macOS Apple Silicon——的签名安装包与更新包：

1. 推送 `vX.Y.Z` 标签（严格 SemVer），或手动触发 `build-desktop` 工作流并填 `version`；**手动触发只保留产物与清单，不创建 Release、不更新 ESA EdgeKV**。
2. 矩阵任务构建并签名各平台产物，`prepare-release` 汇总生成 `desktop-release-manifest.json`。
3. 标签推送时 `release` 任务创建/更新对应的 GitHub Release，并上传全部资产。
4. GitHub Release 成功后，`publish-esa-release` 任务自动校验清单并导入 EdgeKV，客户端与官网随即读取新版本。OSS 上传或 GitHub Release 失败时不会更新 EdgeKV。

**构建矩阵是「实际构建了哪些平台」的唯一来源。** 清单脚本 `scripts/build-desktop-release-manifest.mjs` 按「artifact 目录是否存在」决定清单里包含哪些平台，导入脚本只发布清单里实际存在的平台。因此**恢复某个平台只需在矩阵里加回一条 `include` 条目**，不需要改动任何脚本——该平台的构建步骤（按 `runner.os` 门控）也一直保留在 workflow 里。

代价是目录名写错时该平台会被静默跳过（只打一行提示），`scripts/build-desktop-workflow.test.mjs` 会反向核对矩阵 `artifact` 与清单脚本的 `artifactDirectory`，把这类漂移挡在 CI 之前。

**官网下载页需要另外同步一处。** `edge/site-server.mjs` 的 `DOWNLOAD_PLATFORMS` 决定页面展示哪些平台的下载卡片——它是 Edge 运行时，读不到仓库里的构建矩阵，只能自带一份清单。恢复或新增平台时**要把它一并加进去**，否则平台构建出来了却没有下载入口。方向性错误则由测试兜住：`edge/site-server.test.mjs` 核对 `DOWNLOAD_PLATFORMS` ⊆ 构建矩阵，杜绝「页面列出了 CI 不构建的平台，按钮点了必然 404」；同一份清单还决定页面读取哪些 EdgeKV 记录，所以已下架平台的残留记录不会被渲染出来。

更新服务由 `edge/` 的 ESA 边缘函数提供。下面是完整操作步骤。

## 前置条件（一次性）

1. **凭证**：已执行 `esa-cli login`（脚本自动复用其登录态），或在 CI 中导出环境变量：

   ```bash
   export ESA_ACCESS_KEY_ID=<RAM子账号AK>       # 需授权 AliyunESAFullAccess
   export ESA_ACCESS_KEY_SECRET=<RAM子账号SK>
   ```

   凭证优先级：环境变量 > `~/.esa/config/default.toml`（esa-cli 登录态）。

2. **命名空间**：默认读取 `edge/config.js` 的 `KV_NAMESPACE`（该文件已 gitignore，仅本机存在）。更新记录与卡密共用同一个命名空间，可用 `--namespace <名称>` 临时覆盖。

3. **服务已部署**：`edge/` 代码已通过 `npm run esa:commit && npm run esa:deploy` 上线。

4. **GitHub 仓库变量**（发布构建用，均为 Variable，除备注外）：

   | 变量 | 值 |
   | --- | --- |
   | `VITE_LICENSE_SERVER_URL` | ESA 边缘函数域名，**只填 origin**，例如 `https://bframe.atmomo.cn` |
   | `VITE_LICENSE_RESPONSE_KEY` | 授权响应 HMAC 密钥，与 `edge/config.js` 的 `HMAC_SECRET` 一致 |
   | `VITE_ENABLE_UPDATER` | 设为 `true` 才启用客户端更新检查 |
   | `ESA_KV_NAMESPACE` | EdgeKV 命名空间，必须与线上 `edge/config.js` 一致；当前为 `bv_studio` |

   更新端点不用单独配置：`scripts/write-tauri-release-config.mjs` 从 `VITE_LICENSE_SERVER_URL` 取出 origin，自动拼成 `{origin}/api/desktop-updates/latest?platform={{target}}`。因此该变量**不能带路径或结尾斜杠**，脚本会直接报错。

   自动发布还需在 GitHub Secrets 配置 `ESA_ACCESS_KEY_ID` 与 `ESA_ACCESS_KEY_SECRET`。它们只传给标签发布后的 EdgeKV 导入步骤。

   前两项只在**发布构建**时经环境变量注入，不会改写仓库里的 `src-tauri/tauri.conf.json`。`VITE_ENABLE_UPDATER` 不是 `true` 时更新端点为 `[]`，客户端编译期即关闭更新检查，不会发起任何请求。

   > 提醒：变量仅在 workflow 的 `env:` 里被引用后才会进入构建环境，只在仓库设置里创建一个同名变量没有任何效果。`scripts/build-desktop-workflow.test.mjs` 会守住这条接线。

5. **产物托管（可选，但国内发布强烈建议）**：把安装包/更新包放到阿里云对象存储 + CDN，客户端更新与官网下载页都会指向它。

   | 名称 | 类型 | 值 |
   | --- | --- | --- |
   | `RELEASE_ASSET_BASE_URL` | Variable | 公开基址，**只填域名**，例如 `https://download.atmomo.cn`。不要带应用名或版本号 |
   | `OSS_REGION` | Variable | Bucket 所在地域的 Region ID，例如 `cn-hangzhou`（不带 `oss-` 前缀） |
   | `OSS_ENDPOINT` | Variable | Bucket 所在地域的外网 endpoint，例如 `oss-cn-hangzhou.aliyuncs.com` |
   | `OSS_BUCKET` | Variable | 存放产物的 Bucket 名 |
   | `OSS_ACCESS_KEY_ID` | Secret | 上传用 RAM 凭证，建议只授予该 Bucket 的 `oss:PutObject` / `oss:ListParts` / `oss:AbortMultipartUpload` |
   | `OSS_ACCESS_KEY_SECRET` | Secret | 同上 |

   CI 会自动拼出 `{基址}/{应用名}/releases/v{版本}`，并把各平台产物上传到 OSS 的**同名路径**下。应用名取自 `package.json` 的 `name`（`bframe-studio`）——下载域名可能同时托管多个应用，靠这一层隔离；不用 `tauri.conf.json` 的 `productName`，因为它含空格，进 URL 会被编码成 `%20`。

   例：`https://download.atmomo.cn/bframe-studio/releases/v0.4.0/BFrame%20Studio_0.4.0_aarch64.dmg`

   三项约束必须同时满足：

   - **CDN 回源要保留路径**。对象键是 `{应用名}/releases/v{版本}/{文件名}`，CDN 若做了路径重写，公开地址与对象键就对不上。
   - **不能对包做转码或重新压缩**。上传的必须是签名后的原始字节，否则 `.sig` 与 sha256 全部失效。
   - **文件名字节要一致**。CDN/OSS 上不要重命名文件，清单里的 `fileName` 就是对象键的最后一段。

   只配置了 `RELEASE_ASSET_BASE_URL` 而缺 OSS 凭证时，上传步骤会直接报错中止；完全不配置时整步跳过，产物地址回退到 GitHub Release，行为与从前一致。

## 一、标准发布流程

```bash
# 1. 推送严格 SemVer 标签，触发 build-desktop 工作流
#    （矩阵构建 + 签名 → 生成清单 → 上传对象存储 → 发布清单 artifact）
git tag v0.4.0 && git push origin v0.4.0

# 2. release 和 publish-esa-release 任务会依次自动完成

# 3. 核对线上响应
curl -i 'https://bframe.atmomo.cn/api/desktop-updates/latest?platform=macos-arm'
```

如果自动导入失败，从 Release 资产或 `bframe-studio-desktop-release-manifest` workflow artifact 取回 `desktop-release-manifest.json`，可先空跑再手工补发：

```bash
npm run esa:import-release -- --manifest ./desktop-release-manifest.json --notes "修复导出偶发失败" --dry-run
npm run esa:import-release -- --manifest ./desktop-release-manifest.json --notes "修复导出偶发失败"
```

`--dry-run` 输出就是将要写入 EdgeKV 的完整记录（含每个平台的更新包与安装包地址）。正常标签发布会由 CI 直接执行同一个导入脚本。

第 1 步里 CI 已经**先校验清单、再上传产物、最后才发布清单**：产物上传失败会让整个 job 失败，因此不会出现「清单指向对象存储上不存在的文件」的中间状态。清单里的地址是否指向自建源，取决于有没有配置 `RELEASE_ASSET_BASE_URL`，用 `--dry-run` 一眼就能看出来。

## 二、参数表

| 参数 | 必填 | 说明 |
| --- | --- | --- |
| `--manifest <path>` | 否（默认 `desktop-release-manifest.json`） | 发布清单路径 |
| `--notes "<文本>"` | 否 | 更新说明，进入客户端「更新内容」 |
| `--notes-file <path>` | 否 | 从文件读更新说明（与 `--notes` 二选一，优先） |
| `--force-update` | 否 | 标记为强制更新，客户端启动即弹出不可关闭的更新提示 |
| `--pub-date <RFC3339>` | 否 | 覆盖 `pub_date`，默认取清单的 `generatedAt`（必须带时区） |
| `--allow-downgrade` | 否 | 允许用工更低版本覆盖已发布版本 |
| `--namespace <名称>` | 否 | 覆盖默认命名空间 |
| `--dry-run` | 否 | 只校验并打印将写入的记录，不上传 |

脚本**先全量校验再整体写入**：清单里任一平台任一项不合格（版本非 SemVer、签名为空、`fileSize` 非正整数、更新包或安装包地址不合法、`pub_date` 无时区）都会整批中止并以退出码 1 结束，不会出现「部分平台已更新」的中间状态。

平台集合取自清单本身，**不再要求五平台齐全**。清单里没有的平台（本次未构建）不会中止导入，但会打印一行提示——这些客户端本轮收不到更新，其已发布记录（若存在）继续指向上一版本。

`putKv` 是幂等的：写一半失败时重跑同一命令即可补齐，不会产生重复记录。

## 三、强制更新

```bash
npm run esa:import-release -- --manifest ./desktop-release-manifest.json \
  --notes "为修复数据损坏问题，此版本必须更新" --force-update
```

克制使用。`--force-update` 写出的 `isForceUpdate: true` 会让所有低于该版本的客户端**启动即被不可关闭的弹窗拦住**，包括正在导出工程或离线编辑的用户。建议只在数据损坏、协议不兼容或安全问题这类「旧版本继续用会出事」的场景使用。

强制状态是发布记录的一个属性，不写入发布清单。需要撤回时重新导入同版本、不带 `--force-update` 即可覆盖（同版本导入会打印告警后覆盖）。

## 四、更新说明

```bash
npm run esa:import-release -- --manifest ./desktop-release-manifest.json --notes-file CHANGELOG.md
```

说明文本会原样显示在更新弹窗里，建议一段话、面向用户描述变化，不要粘贴 commit 列表。留空则客户端不显示「更新内容」区块。

## 五、回滚与降级

发布记录按平台独立，回滚某个平台只需重新导入一份对应版本的清单：

```bash
# 让 0.4.0 重新指向更早的 0.3.x 清单（必须显式允许降级）
npm run esa:import-release -- --manifest ./desktop-release-manifest.json.0.3.2 --allow-downgrade
```

默认拒绝降级是有意的：重跑一份旧 tag 的清单如果静默生效，会把全体客户端推回旧版本。需要回滚时请确认目标清单确实指向你想要的产物。

> 已经升级到新版的客户端不会因为服务端回滚而降级——Tauri updater 只在 `release.version > current_version` 时提示更新。回滚的实际效果是**阻止还没升级的用户升到问题版本**。

彻底下线某个平台的更新提示，用 `esa:clear-kv` 删掉指针键，客户端随后收到 204：

```bash
npm run esa:clear-kv -- --prefix release:latest: --dry-run
npm run esa:clear-kv -- --prefix release:latest:
```

## 六、清理

```bash
npm run esa:clear-kv -- --prefix release:                        # 清全部发布记录
npm run esa:clear-kv -- --prefix release:latest:macos-arm        # 只清某个平台
```

`clear-kv` 会同时影响卡密与设备记录，加 `--prefix` 限定范围，先 `--dry-run` 看一遍。

## 七、本地验证链路

```bash
npx vitest run edge/        # 边缘函数纯逻辑与请求处理层
npm run test:release        # 发布脚本测试（含清单校验与跨模块契约）

npm run esa:dev             # 本地起边缘函数，可在根目录放 kv.json 模拟 EdgeKV 数据
curl -i 'http://localhost:<port>/api/desktop-updates/latest?platform=macos-arm'
```

本地 `esa:dev` 里手工构造一条 `release:latest:macos-arm` 记录，就能在不碰线上的前提下验证响应字段。

只想确认「域名 → 更新端点」拼对了、不真正构建时：

```bash
set -a && . ./.env.production && set +a
export RELEASE_VERSION=0.4.0 TAURI_SIGNING_PUBLIC_KEY=<任意非空值> RUNNER_TEMP="$(mktemp -d)"
npm run release:config
cat "$RUNNER_TEMP/bframe-studio-release/tauri.release.conf.json"   # 看 plugins.updater.endpoints
```

## 八、产物命名与体积口径

生成的安装包 / 更新包对：

| 平台 | 安装包 | 更新包（Release 资产） | 当前是否构建 |
| --- | --- | --- | --- |
| `windows-x86` | NSIS 签名 `.exe` | 同一个 `.exe`（NSIS 被动安装） | ✅ |
| `macos-arm` | `.dmg` | `BFrame Studio_arm64.app.tar.gz` + `.sig` | ✅ |
| `windows-arm` | NSIS 签名 `.exe` | 同一个 `.exe` | ⛔ 未构建（`windows-11-arm`） |
| `macos-x86` | `.dmg` | `BFrame Studio_x64.app.tar.gz` + `.sig` | ⛔ 未构建（`macos-15-intel`） |
| `linux-x86` | `.AppImage`（同时发布 `.deb`） | `{AppImage 文件名}.tar.gz` + `.sig` | ⛔ 未构建（`ubuntu-24.04`） |

命名口径分三层，不要混淆（macOS 部分已由真实打包确认）：

- **`.app` 目录名与安装包名**取 `tauri.conf.json` 的 `productName`（`BFrame Studio`）。Tauri 生成 `BFrame Studio.app.tar.gz`，CI 再追加架构后缀得到 `BFrame Studio_arm64.app.tar.gz`。
- **可执行文件名**取 Cargo 包名（`bframe-studio`），即 `BFrame Studio.app/Contents/MacOS/bframe-studio`；Windows 安装后同样是 `bframe-studio.exe`。
- **CI 产物目录前缀**是 `bframe-studio-`（如 `bframe-studio-macos-arm64`）。`.github/workflows/build-desktop.yml` 的 matrix `artifact` 必须出现在 `scripts/build-desktop-release-manifest.mjs` 的 `artifactDirectory` 清单里——对不上的平台会被清单脚本静默跳过、永不发布，这条漂移由 `scripts/build-desktop-workflow.test.mjs` 反向核对拦截。

各平台最终文件名以 `desktop-release-manifest.json` 的 `fileName` 为唯一权威，`npm run esa:import-release` 按它写入 EdgeKV。

体积参考（macOS arm64 实测）：更新包约 67MB，解压后 App 约 104MB，其中 ffmpeg/ffprobe 两个 sidecar 合计 60MB。Tauri updater 是全量替换、无差分更新，所以每次发版这部分都要重下。

bundle identifier 与应用标识口径见 [`10-应用运行时与平台集成.md`](10-应用运行时与平台集成.md)。

## 常见问题

| 现象 | 原因与处理 |
| --- | --- |
| 客户端不提示更新 | 先 `curl` 端点确认不是 204；再确认发布构建时 `VITE_ENABLE_UPDATER=true` 且 `VITE_LICENSE_SERVER_URL` 已配置（任一缺失，客户端根本不会请求） |
| 构建报 `VITE_ENABLE_UPDATER is true but VITE_LICENSE_SERVER_URL is not set` | 开了更新开关但没配域名。补上 `VITE_LICENSE_SERVER_URL`，或把开关设为非 `true` |
| 构建报 `must contain only the origin` | `VITE_LICENSE_SERVER_URL` 带了路径、查询串或结尾斜杠；只填 `https://域名` |
| `platform 参数缺失或不受支持` | 端点模板里的 `{{target}}` 占位符丢失，或被写成了 `darwin-aarch64` 之类的 Tauri 默认目标名 |
| `更新包元数据不完整`（503） | 该平台记录缺 URL/签名/文件大小，通常是手工改过 KV。重新跑 `esa:import-release` 覆盖 |
| 导入报 `已发布版本 x 高于待导入的 y` | 保护机制命中。确认确实要回滚时加 `--allow-downgrade` |
| 导入报 `sourceUrl 不是合法的 https 地址` | 非 tag 推送的构建产物 `sourceUrl` 为 null，由脚本按 `repository` + `tag` 推导；若清单里已有非空但非 https 的值，说明清单被改坏，需重新生成 |
| `Throttling.Api: Request was denied due to user flow control` | ESA OpenAPI 限流。脚本自动退避重试 5 次；只有 5 条记录，重跑即可 |
| 导入成功但客户端仍收不到 | EdgeKV 最终一致，全球同步需数秒到几十秒，稍后重试 |
| 升级后客户端报签名校验失败 | 产物在签名后被重新打包，哈希已变。必须发布未重新压缩的原始产物 |
| Windows 用户升级后需要手动退出应用 | 可执行文件名由 `tauri-base` 改为 `bframe-studio`，NSIS 的「应用是否在运行」检查按新名匹配，匹配不到旧进程名。属一次性的历史遗留问题，之后版本不再出现；旧 `tauri-base.exe` 可能残留在安装目录，手动删除即可 |
| Release 页面标题仍是旧的模板名 | 标题只在 `gh release create` 时写入，已存在的 Release 走 `gh release upload --clobber` 分支，上传资产不会改写标题。新标签自动使用 `BFrame Studio <tag>`；旧 Release 用 `gh release edit <tag> --title "BFrame Studio <tag>"` 或网页端手动改标题 |
| 构建报 `RELEASE_ASSET_BASE_URL is not a valid URL` / `must use HTTPS` | 该变量**只填域名**，比如 `https://download.atmomo.cn`，且必须 https；应用名与版本号由 CI 追加 |
| 构建报 `无法从 package.json 读取应用名` | 产物路径的应用名子目录取自 `package.json` 的 `name`，读不到就直接失败而不是猜路径。检查仓库根 `package.json` 是否完整 |
| 构建报 `RELEASE_ASSET_BASE_URL 已配置，但缺少 OSS_*` | 配了自建源却没配齐地域、桶或凭证。补齐 `OSS_REGION` / `OSS_ENDPOINT` / `OSS_BUCKET` 与两个 Secret，或干脆清空 `RELEASE_ASSET_BASE_URL` 回到 GitHub 源 |
| 构建在 `Upload release assets to Aliyun OSS` 步骤报 `region must be set in sign version 4` | ossutil 2.x 默认使用 V4 签名，必须知道 Bucket 地域。将 `OSS_REGION` 设为 OSS 控制台显示的 Region ID（如 `cn-hangzhou`，不带 `oss-` 前缀），并确保与 `OSS_ENDPOINT` 对应 |
| 清单里的地址仍是 `github.com` | 没配 `RELEASE_ASSET_BASE_URL`。这是正常的回退行为，不是错误 |
| 客户端能检测到更新但下载失败 | 先直接 `curl -I` 清单里那条 `url`。404 多半是对象存储路径与 `RELEASE_ASSET_BASE_URL` 不匹配（CDN 做了路径重写），或产物没上传成功 |
| 下载到的 macOS 包是 `.app.tar.gz` 而不是 DMG | 官网下载页用了更新包地址。检查导入记录里的 `installerUrl`：老记录没有该字段时会退回 `url`，重新跑一次 `esa:import-release` 即可 |
| 上传成功但部分文件缺失 | 批量上传（`cp -r`）默认「出错记 report 后继续」，job 仍成功。CI 已改为逐文件 `cp`，单个文件失败即以非零码退出；若仍缺文件，先看 job 日志里的 ossutil 输出与 report |
| 构建在 `Upload release assets to Aliyun OSS` 步骤报 `Error: unknown flag: --disable-ignore-error` | ossutil 2.x 没有 1.x 的同名开关。该开关已被移除，改用逐文件 `cp`（失败即非零退出），不要再加回来；`--no-error-report` 仅关闭报告文件，不改变退出码语义 |
| 构建在 `Install ossutil` 步骤报 `chmod: cannot access '.../ossutil'` | 官方 zip 内含一层 `ossutil-<版本>-linux-amd64/` 目录，解压后二进制不在 `ossutil-bin/ossutil`。CI 已改用 `unzip -j` 扁平化解压；若仍失败，日志会打印 `unzip -l` 的实际结构供定位 |
| 官网下载页出现点了必然 404 的按钮 | `edge/site-server.mjs` 的 `DOWNLOAD_PLATFORMS` 列了构建矩阵不产出的平台。删掉该平台并重新部署边缘函数；`edge/site-server.test.mjs` 的反向核对会提前拦住 |
| 官网下载页缺少某个平台的入口 | 该平台已加进构建矩阵，但 `DOWNLOAD_PLATFORMS` 没同步。补上后重新部署边缘函数 |
| 官网下载页仍显示已下架平台 | 页面只读 `DOWNLOAD_PLATFORMS` 内的 EdgeKV 记录，残留的 `release:latest:{platform}` 不会被渲染。若仍出现，说明常量没改或边缘函数未重新部署 |
| 官网各平台版本号不一致 | 每个平台读自己的 `release:latest:{platform}`，某个平台未导入就停在旧版本。重新导入清单，或确认该平台是否还在 `DOWNLOAD_PLATFORMS` 中 |
| macOS Intel / Linux 访客看不到下载按钮 | 属预期行为：访客系统没有对应构建时，脚本会隐藏 hero 区的智能下载按钮，避免引导到无法运行的文件；下载区仍展示已构建平台的卡片 |
